# Reliability and managed completions

Status: ready-for-agent

## Problem Statement

`bin` must safely turn provider artifacts into managed installations without treating remotely derived names, release metadata, checksums, archives, or generated shell code as trusted. Current selection can favor packaging or archive depth over product identity; generic URLs bypass common archive processing; checksum association can bind a digest to the wrong bytes; and replacement/config persistence can leave an installation inconsistent after failure. The observed Darwin ARM64 metadata-sidecar and multi-app DMG cases demonstrate these gaps.

The project also needs opt-in, native-first managed Bash, Zsh, and Fish completions for installed commands. This must not turn a successful binary installation into a failure, execute downloaded programs without permission, modify shell startup files, or interfere with Cobra's existing `bin completion <shell>` command.

## Solution

Deliver three ordered milestones:

1. **Safety and integrity.** Contain untrusted names; bind checksums to exact download or installed bytes with explicit outcomes; close/clean resources; atomically replace direct binaries; and reconcile executable and config state on persistence failures.
2. **Deterministic artifact processing.** Build a bounded, owned artifact inventory shared by release and generic-URL downloads; resolve target, product, variant, and archive member identity before packaging/depth preferences; retain selection intent across lifecycle operations; select DMG bundles by identity; and add non-mutating JSON inspection.
3. **Managed completions.** Add disabled-by-default policy, bundled-script discovery, bounded opt-in generator execution, ownership-safe shell installation, and lifecycle/sync/remove integration for Bash, Zsh, and Fish.

Complete milestone 1 before selection restructuring, milestone 2 before automatic completion discovery/generation, and keep provider transport, asset processing, command orchestration, config persistence, system-package handling, and completion management at their existing architectural boundaries.

## Implementation Decisions

- Preserve the Go application, Cobra command conventions, provider interfaces, lifecycle strategies, config locking, payload validation, release lanes, pinning, minimum age, aliases, and system-package metadata. Direct-binary transactions and system-package installation retain distinct semantics.
- Treat upstream executable names as untrusted single components, archive members as validated relative identities, and user destinations as intentional filesystem paths. Do not make malicious input acceptable through cleaning, basing, or repeated sanitization. Encode provider/version cache material as a stable contained component without changing stored version identity.
- Use explicit checksum applicability, parsing, binding, and verification outcomes. Prefer supported GitHub release-asset digests, then strict applicable manifests. An authoritative mismatch/failure cannot fall back to another source; signatures remain excluded.
- Stage direct-binary replacement beside the destination; complete copy, hash, validation, mode, and close before platform-specific replacement. Retain rollback material through config commit under a short cross-process install/config lock; keep downloading, prompting, and validation outside it. Define recovery state for rollback failure and isolate Go-install output before promising replacement safety.
- Use a small owned artifact-processing result containing executable metadata, transformation/integrity metadata, and inventory. Classify executable, completion, and ignored entries; enforce finite configurable download/entry/expanded/nesting budgets while streaming all layers; account for ignored bytes; reject unsafe/duplicate normalized identities; use random staging locations and one cleanup owner.
- Apply an outer artifact-kind boundary before platform/name ranking. Metadata/data sidecars, including notarization JSON, cannot become executable candidates; opaque executable downloads remain possible only through payload validation. Supported-format classification and decoding share one definition; recognized Zstandard is explicitly unsupported until a decoder is intentionally added.
- Resolve member and release candidates in pure reusable steps with typed reasons/errors suitable for JSON diagnostics. Product/target/variant identity precedes package format and depth. Narrow wrapper normalization preserves meaningful internal directories. Explicit choices never bypass containment, target compatibility, or runnable-payload validation.
- Persist an optional selection descriptor for logical product, applicable target/ABI/CPU constraints, and archive-member identity through fetch, install, update, ensure, config cloning/mutation, and portable export/import. Old records derive only supported intent; preserve `RemoteName`, `SourceAsset`, `PackagePath`, release lane, and existing system-package fields.
- Reuse persisted `AppBundle` rather than adding or overloading identity fields. Validate selected DMG bundle containment and source executable before copy/signing; persist selected bundle and installed executable together. DMG replacement-failure semantics are not expanded beyond this selection/pre-copy scope.
- Make inspection reuse read-only HTTP artifact resolution and redact secrets. Effectful Docker and Go-install inspection are rejected before version discovery/fetch; temporary bounded downloads are cleaned.
- Completion policy is disabled by default. Store machine-local per-binary/per-shell records for source, generator/member identity, installed command/path, binary/script hashes, adapter version, ownership, status, and actionable reason. Keep local paths, ownership, cached status, and permission out of portable export/import; cache only successful/unsupported outcomes keyed by relevant binary/shell/adapter/override identity, not transient failures.
- Prefer applicable bundled completion evidence over generation. Native generation supports only recognized command shapes and explicit structured argv overrides; it is a constrained execution boundary, not a sandbox or trust proof. Parsing/registration validates format only.
- Completion ownership is recorded after successful write and protects only the recorded unmodified file. State/write failures roll back or leave a repairable result. Existing lifecycle hooks remain at their documented boundaries; completion errors occur after successful binary commit and never convert it into an install failure.
- Exclude PowerShell completions, signature verification, a plugin framework, generic help-to-completion compilation, arbitrary generator probing, shell-startup-file editing, elevation for generation, live-release-dependent acceptance, and privileged package installation from this work.

## Testing Decisions

- Add behavioral regressions at existing seams, reusing synthetic archives, `httptest`, controlled helper executables, existing fixtures/helpers, mocked platform tools, and isolated `BIN_CONFIG`, `BIN_EXE_DIR`, `HOME`, XDG, cache, and applications locations. Do not use developer state, live releases, or privileged installs.
- Exercise user-visible install/update/ensure/remove/prune/inspect/completions flows at the command-level lifecycle seam, including preservation after failed replacement/config writes, no pre-copy DMG side effects, read-only inspect, completion warning/repair behavior, and existing aggregate update continue-on-error/exit-code behavior.
- Exercise deterministic logic at pure provider/asset resolver and checksum seams: unsafe names; checksum parsing/binding/outcomes; sidecars; formats/budgets/cleanup; identity-first archive/product resolution; AgentsView Darwin ARM64 selection; AppImage compatibility; generic URL processing; stored selection across versions; and stable rejection reasons independent of input order.
- Exercise persistence through config serialization and locking seams: backward-compatible optional fields, installed-hash/integrity scope, selection descriptor, AppBundle continuity, export/import isolation, concurrent transaction merge/rollback, and local-only completion state.
- Use controlled process/filesystem adapters only where platform behavior requires them: Unix/Windows replacement and locked-file behavior, Go build output isolation, DMG mount/copy/signing invocation boundaries, completion generator timeout/output/child-tree/environment rules, shell paths, symlinks, ownership, and setup-file non-mutation.
- Include focused tests with each TODO, `mise run lint`, and `mise run test-race` for filesystem, ownership, process, locking, or concurrent-state changes. Suggested focused commands include `mise exec -- go test ./cmd ./pkg/assets ./pkg/providers`, package-specific checksum/asset/config/completion tests, and the DMG-focused command test selection.
- At each milestone exit run `mise run test` and `mise run verify`; run `mise run build` for CLI changes. Run native Linux/macOS/Windows replacement/process/filesystem tests and Unix shell integration acceptance where available; do not claim unavailable platform or live-provider coverage. Run Action tests only if Action files change.

## Out of Scope

- PowerShell completion support.
- Signature verification or claims that source digests authenticate a publisher.
- Plugin architecture, parallel installer, generic help-to-completion compiler, arbitrary completion-subcommand guessing, or a Zstandard decoder.
- Editing shell startup files, loading completions into the current shell, elevating to generate completions, and changing package-manager-owned completion files.
- Effectful Docker or Go-install inspection, routine live-provider testing, and privileged system-package acceptance.
- Extending DMG replacement transaction semantics beyond deterministic selection and pre-copy validation.
